# The CRDs of Argo CD

## What a CRD is in the first place

CustomResourceDefinition. The mechanism that **adds your own resource types** to the Kubernetes API.

- Once a CRD is installed, `kubectl get <new type>` works (= one more API and one more place to keep data)
- But a CRD is only a type definition. **It only means something when paired with a controller that reads it and acts**
  (this pair of "custom resource + controller" is called the operator pattern)
- Installing Argo CD can be read as installing "3 CRDs + the controllers that reconcile them"

```bash
kubectl --context kind-demo-hub get crd | grep argoproj
# applications.argoproj.io / applicationsets.argoproj.io / appprojects.argoproj.io
```

## 1. Application: the declaration of what to sync, where, and how

The central resource of Argo CD. 1 Application = 1 unit of deployment.

```yaml
spec:
  project: demo                    # the AppProject it belongs to (the authorization boundary)
  source:                          # what (which part of Git to render)
    repoURL: http://gitea.../manifests.git
    targetRevision: HEAD
    path: app/web/overlay/dev/demo-app
  destination:                     # where
    name: spoke-dev                # registered cluster name (or server: URL)
    namespace: demo-app
  syncPolicy:                      # how to sync (automated / prune / selfHeal ...)
```

There are two axes of status to watch: `sync.status` (Synced / OutOfSync = does it match Git) and
`health.status` (Healthy / Progressing / Degraded = are the resources themselves well).
"Synced but Degraded" (applied exactly as in Git, but the app is down) is possible. The two axes are independent.

This lab creates Applications in two ways:

- **Generated by an ApplicationSet** (demo-app etc.): mass production driven by markers. See the section after next
- **Written by hand and applied** (`gitea` / `vault` in `hub/platform.yaml`): enough for a handful of platform components.
  The destination is `name: in-cluster`, the built-in registered name by which Argo CD refers to the cluster it runs in
  (`https://kubernetes.default.svc`), so the hub deploys to itself.
  Gitea is the chicken-and-egg case of managing the Git server's own manifest in that Git, so
  a script applies it directly the first time only, and the Application **adopts** the existing resources
  (if a resource of the same name is live, Argo CD simply takes over managing it)

## 2. AppProject: the authorization boundary of Applications

The allowlist of which repositories the Applications in this project may use as a source,
which cluster x namespace they may sync to, and which cluster-scoped resources they may create.

```yaml
spec:
  sourceRepos: [http://gitea.../manifests.git]   # repositories allowed as a source
  destinations:                                   # allowlist of sync destinations
    - name: spoke-dev
      namespace: demo-app
  clusterResourceWhitelist:                       # cluster scope: only the kinds listed here
    - group: ""
      kind: Namespace
```

- The standard use is as a per-team **multi-tenant boundary** (combined with RBAC to build
  "team X can only touch the Applications of project X")
- A sync outside the allowed range is rejected at sync time. Scenario 6 of the lab lets you see it
- The `default` project has no restrictions, so the usual practice is not to use it in real operations

## 3. ApplicationSet: the mass-production mechanism for Applications

Generates Applications in bulk from a **generator (the data source) x a template (the Application blueprint)**.

```yaml
spec:
  generators:
    - git:                       # git generator (files): looks for config files in the repository
        repoURL: http://gitea.../manifests.git
        files:
          - path: "app/*/overlay/dev/*/app.argocd.yaml"
  template:                      # 1 file found = 1 Application
    metadata:
      name: '{{ .name }}'        # the file content is fed in as variables
    spec:
      source:
        path: '{{ .path.path }}' # where the file sits is a variable too
      ...
```

The `app.argocd.yaml` (marker) of this lab is this config file. The properties to keep in mind:

- **Opt-in**: only apps that have the file are generated. Placing it = deployment starts, removing it = the whole Application is deleted
- **The file content becomes the template parameters** (name / namespace / env and so on).
  The location (path) itself is data too (`{{ .path.path }}`)
- A generated Application is owned by the ApplicationSet. Editing it by hand gets it reverted to the template.
  So the split is: policy lives in the template (the admin), identity data lives in the config file (the user)
- Besides git files there are many generators, such as list / cluster / matrix. Fan-outs like "N similar apps"
  or "M clusters x N apps" take a few lines

## Not a CRD, but you need to know it: the registry of labeled Secrets

For registering what it connects to, Argo CD uses not CRDs but **Secrets with the label `argocd.argoproj.io/secret-type`**.

| secret-type | What it registers |
|---|---|
| `cluster` | A destination cluster (name / server URL / auth) |
| `repository` | Connection info of a single repository |
| `repo-creds` | An auth template per URL prefix (applies to every repo under it) |

This lab only uses cluster registration. The structure of the Secret is in `hub/clusters.yaml` (the template), and
`scripts/04-spokes.sh` fills in the dynamic value (server) and the secret (bearer token) during setup.
